# Baseline integrity

A growth check is useful only when its previous inventory is complete and belongs to the
same package. Baselines are validated when created, loaded, and compared.

Validation requires a supported schema, a canonical package root, an object inventory,
non-negative safe-integer byte counts, and a total equal to the sum of file sizes. When
present, category totals, file counts, and group sizes must also be consistent. Inventory
paths cannot be absolute, contain parent traversal, backslashes, NUL, or ambiguous segments.
Comparing a baseline for a different package root is an input error.

## Missing versus disabled

No configured baseline (`baseline.path: null`) leaves growth comparison disabled. An
explicitly configured baseline that is missing is now an error, not a successful audit
without a growth check. Corrupt JSON and inconsistent evidence also fail before comparison.
The CLI uses its existing tool/input-error exit code (2); ordinary growth findings retain
their existing rule IDs and severity behavior.

## Initial creation and intentional reset

Start with `baseline.path` unset or null. Run an audit with
`--write-baseline .packguard-baseline.json`, review and commit the inventory, then configure
that path for future audits. To replace a deliberately invalid/missing baseline, explicitly
disable the input baseline during that one reviewed generation run; do not suppress an
input error in CI. Valid existing schema-version-1 baselines generated by PackGuard retain
the same wire format.

## Limits

This checks structural and arithmetic integrity, not authenticity. A contributor who can
change a valid baseline can still adjust budgets or replace the entire inventory. Review
baseline changes against a trusted revision. A matching root does not prove identical
ignore patterns or platform compiler output. Reports and fixtures contain no product data.
